Управление рабочим столом Windows для агентов MCP. Сначала дерево доступности,
пиксели только когда ничего другого не осталось, ввод через WinAPI. Node.js и
встроенный в Windows PowerShell: без Python, без `uvx`, без компилятора, без
нативных модулей.

GitHub отдаёт оба файла как скачивание, а не как видео, поэтому здесь GIF.</sub></p>

На видео обычное WinForms-приложение (`examples/demo-app.ps1`). Пять действий, ноль
пиксельных кликов, и курсор все 24 секунды лежит в поле лога, а работу делают
`ValuePattern` и `InvokePattern`, которые заполняют поле, запускают поиск,
перезагружают список, помечают посылку доставленной и копируют её номер.
Повторить: `node examples/demo.mjs`, а с `--pause 1500` видно каждый шаг отдельно.

## Почему это, а не скриншотный цикл

- **Целиться по смыслу, а не по пикселям.** `computer_find { name: "Search" }`
  отдаёт элемент вместе с его `automationId`, прямоугольником и списком
  поддерживаемых паттернов. Координата со снимка к моменту клика уже протухла.
- **Четыре слоя чтения, и ответ говорит, какой ответил.** UI Automation, затем
  MSAA через `oleacc`, затем Chrome DevTools Protocol для страниц Chromium, затем
  OCR на движке внутри Windows. Пустое дерево от UIA означает переключиться дальше.
- **Зависшее окно не убивает агента.** UI Automation ходит в чужие приложения по
  COM и не отступает перед замороженным. Каждый вызов идёт на STA-потоке с жёстким
  таймаутом, а после таймаута ключ `инструмент|окно` блокируется на 90 с. Остальные
  окна продолжают работать.
- **Ноль внешних бинарников.** Установка это `npm install`: ни Visual C++ Build
  Tools, ни Python, ничего собирать. Именно это держит `npx desk-mcp` рабочим на
  машине, где компилятор никогда не стоял.

## Установка

```bash
npm install -g desk-mcp
```

или из клона:

```bash
git clone https://github.com/DigitalDog1/desk-mcp.git
cd desk-mcp
npm install
```

Требуется Node.js 20+ и Windows 10 1809 или Windows 11.

### Подключение

`claude_desktop_config.json`, `mcp.json` или любой другой конфиг клиента:

```json
{
  "mcpServers": {
    "desk-mcp": {
      "command": "npx",
      "args": ["-y", "desk-mcp"]
    }
  }
}
```

Для клона вместо `npx` укажи `node`, а в `args` путь к `server.mjs`. После
перезапуска клиента инструменты доступны.

## Первый результат за 60 секунд

```bash
# 1. окно для работы (английские подписи, каждое действие пишется в само окно)
powershell -NoProfile -ExecutionPolicy Bypass -STA -File examples\demo-app.ps1

# 2. сторона агента: найти по смыслу, записать через ValuePattern,
#    нажать через InvokePattern и проверить результат
node examples/demo.mjs
```

```
--- 1. Найти окно "Parcel Tracker" и кнопку Search по automationId
{
  "count": 1,
  "elements": [
    {
      "name": "Search",
      "type": "Button",
      "id": "btnSearch",
      "class": "WindowsForms10.BUTTON.app.0.ab05f7_r37_ad1",
      "rect": { "x": 530, "y": 173, "w": 120, "h": 32 },
      "enabled": true,
      "offscreen": false,
      "patterns": [ "InvokePattern" ]
    }
  ]
}

--- 3. Записать трек-номер через ValuePattern, без фокуса и без мыши
{
  "ok": true,
  "via": "ValuePattern",
  "value": "ZX-9026-1147",
  "element": { "name": "Tracking number:", "type": "Edit", "id": "searchBox", ... }
}

--- 4. Нажать Search через InvokePattern
{ "ok": true, "via": "InvokePattern", "element": { "id": "btnSearch", ... } }

--- 5. Проверить значение поля, а не только факт клика
{ "ok": true, "checks": [ { "state": "satisfied", "detail": "найдено 1" } ] }

--- 6. Нажать Copy tracking number и прочитать буфер обмена
буфер обмена: "ZX-4471-8820" (12 символов)
```

На локализованной Windows кнопки заголовка приходят с переведёнными именами
(`Закрыть`, `Развернуть`, `Свернуть` на русской сборке). Опирайся на
`automationId`, а не на текст заголовка, иначе агент сломается на языке
пользователя.

Обычный `computer_click` по координатам, поэтому курсор ходит по экрану, а
приложение не видит разницы. WinForms-кнопка при этом игнорирует синтетический

координатах: без наведения счётчик оставался на 0, с наведением событие доходило.
Для пиксельных кликов в незнакомое приложение ставь `hoverFirst: true` по умолчанию.

## Сколько это стоит, в замерах

Токены текста считаются как `символы / 4`, токены картинки по формуле Anthropic
`ширина * высота / 750`. Замерено с запущенной на машине Chromium-игрой, это худший
случай для всего, что ходит в UI Automation.

| Окно | Размер | Один элемент (`computer_find`) | Всё дерево | Компактное дерево | Картинка |
| --- | ---: | ---: | ---: | ---: | ---: |
| MiniMax Code | 2576x1416 | 93 токена, 11 мс | 471 токен, 46 мс | 1313 токенов, 18 мс | 4864 токена, 86 мс |
| Parcel Tracker (WinForms) | 940x640 | 83 токена, 68 мс | 5011 токенов, 256 мс | 3482 токена, 113 мс | 803 токена, 68 мс |
| Edge | 1265x1380 | 94 токена, 11 мс | 4858 токенов, 55 мс | 3697 токенов, 42 мс | 2328 токенов, 35 мс |
| Wallpaper UI | 740x560 | 15 токенов, 100 мс | 1710 токенов, 239 мс | 1492 токена, 22 мс | 553 токена, 50 мс |
| Справка Windows | 2504x1226 | 97 токенов, 10 мс | 3178 токенов, 37 мс | 2436 токенов, 31 мс | 4094 токена, 97 мс |

- Поиск одного элемента дешевле картинки того же окна в 3.2-52 раза и при этом
  отдаёт точные границы и паттерны.
- Всё дерево может стоить дороже скриншота. Оттягивают `maxDepth`, `maxElements`,
  `interactiveOnly`, `compact` и `maxChars`.
- `compact` меняет именованные поля на позиционные массивы и экономит на деревьях
  выше 13-31%. На маленьком дереве он **проигрывает**: легенда `fields` это
  фиксированный накладной расход, и на дереве в 471 токен ответ стал 1313 токенов.
  Включай на большом, выключай на маленьком.
- Картинка стоит одинаково всегда, зависит только от размера окна. Большое окно
  дорого насколько бы пустым ни было.
- Все пути здесь дают 10-256 мс, и при этом на машине работает приложение,
  которое тормозит UI Automation. Пара дней назад та же машина давала 3055-4362 мс
  на один поиск элемента и 3207 мс на чтение дерева, потому что разрешение окна
  шло через `AutomationElement.RootElement`. Теперь оно идёт через `user32`, а
  обход стартует от этого handle, и плохо себя ведущий сосед больше не берёт плату за
всех. Окно находится через `EnumWindows`, чтение идёт из `FromHandle`. Окно находится через `EnumWindows`, чтение идёт из `FromHandle`.
- Полный прогон демо-окна от начала до конца, вместе со стартом воркера:

## 42 инструмента

**Глаза**

- `computer_screenshot`: весь экран, произвольная область или одно окно через
  `PrintWindow`, поэтому работает на перекрытом и свёрнутом окне. PNG или JPEG,
  любой масштаб.
- `computer_ocr`: текст прямо из пикселей движком, встроенным в Windows
  (`Windows.Media.Ocr`, en и ru). Слова приходят с границами, по границе можно
  кликнуть. Про фоллбэк честно: на демо-окне он превратил `ZX-4471-8820` в
  `zx-=v-882C`.

**Дерево интерфейса**

- `computer_read_screen`: UI Automation, автоматический откат на MSAA,
  автоматическое наращивание глубины обхода и OCR, когда оба дерева пусты (тогда в
  ответе есть `backend` и `degraded`).
- `computer_find`: один элемент по имени, роли или `automationId`.
- `computer_element_at`: цепочка элементов под точкой.
- `computer_browser_tree`, `computer_browser_descendants`, `computer_browser_eval`,
  `computer_browser_click`: настоящий DOM страницы по CDP, с готовыми CSS-селекторами
  и кликом, который сообщает, что именно событие поймало.

**Руки**

- `computer_click` (модификаторы, `nudge`, `scale`), `computer_move`,
  `computer_mouse_move`, `computer_drag`, `computer_scroll`, `computer_mouse_button`,
  `computer_type`, `computer_key`, `computer_key_down` / `computer_key_up`,
  `computer_wait`.
- `computer_invoke`: жмёт через `InvokePattern` **без захвата мыши** и без вывода
  окна на передний план. Именно это делает клип выше.
- `computer_set_value`: пишет через `ValuePattern`, тоже без фокуса.
- `computer_batch`: до 50 инструментов за один вызов, шаг за шагом, поэтому
  каждый шаг подчиняется тем же бюджетам.

**Окна и рабочий стол**

- `computer_windows`, `computer_focus`, `computer_wait_window`,
  `computer_active_window`, `computer_window_set_frame`, `computer_close_window`,
  `computer_launch`, `computer_desktop` (виртуальные рабочие столы там, где они
  есть в сборке Windows), `computer_bench`.

**Проверка**

- `computer_verify_state`: предикаты `exists`, `value_equals`, `enabled`,
  `selected`. `unknown` так и остаётся `unknown` и никогда не считается успехом.
- `computer_invoke`, `computer_set_value` и `computer_select_text` отказываются при
  `enabled: false`, потому что `InvokePattern` на заблокированном элементе в
  Windows возвращается довольным и не делает ровно ничего.
- `computer_selftest` проверяет весь канал разом.

## Устройство

```
server.mjs      MCP-сервер на Node поверх stdio, CDP-клиент, circuit breaker
worker.ps1      один долгоживущий PowerShell: user32, UI Automation, MSAA, OCR
uia-native.cs   C# 5: STA-пул с очередью, отменяемый таймаут, перерождение потока
```

Воркер один на весь жизненный цикл сервера, а не процесс на вызов: PowerShell
поднимается около 400 мс, а `Add-Type` компилирует C# дольше. Обмен построчный,
ответы в base64, иначе кириллица ломается на кодовой странице консоли.

| Слой | Что даёт | Когда применяется |
| --- | --- | --- |
| UIA | точные `automationId`, паттерны, границы | нативные и управляемые приложения Windows |
| MSAA | `oleacc`, глубина растёт сама | когда UIA вернула пустое дерево |
| CDP | настоящий DOM страницы с CSS-селекторами | окна Chromium, точные селекторы |
| OCR | слова с границами, без идентичности элементов | игры, видео, GPU-контент |

Порядок выбран потому, что для Chromium первые два почти бесполезны: UIA отдаёт
дерево, обвязанное безымянными `PANEL`, и только если браузер запущен с
`--force-renderer-accessibility`. Ровно ради этого есть слой CDP, и поэтому
`computer_browser_click` умеет отдавать `verified: true` по пробе внутри страницы
без движения мыши.

## Когда окно зависает

Вызовы UI Automation уходят в другой процесс по COM, и приложение с модальным
окном, подвисшим UI-потоком или старым WPF держит RPC открытым навсегда.
`ScriptBlock` в PowerShell нельзя перенести на STA-поток (он привязан к своему
runspace), поэтому переносить пришлось сам обход, в C#. Сервер делает четыре
вещи:

- **`uia-native.cs` гоняет путь чтения на STA-потоке с жёстким таймаутом.** Вызов,
  вышедший за время, отравляет свой поток, следующий получает свежий, а брошенный
  умирает в фоне. Замерено: таймаут срабатывает на 1512 мс при бюджете 1500, а
  следующий вызов отрабатывает за 43 мс на новом потоке (`TID 19 -> 21`).
- **Примерно в семь раз быстрее** заменённого пути на PowerShell: 147 мс против
  1014 мс на одном и том же окне qBittorrent, вывод совпадает, кроме `textLen`,
  который раньше всегда был константой `1` (PowerShell возвращает `.Length == 1`
  для любого скаляра).
- **Circuit breaker, поокночный.** После таймаута ключ `инструмент|окно`
  блокируется на 90 с. Вызовы к этому окну падают мгновенно с объяснением, вместо
  того чтобы снова висеть. Остальные окна не затрагиваются.
- **Жёсткий бюджет 8 с на весь вызов**, с запасом на два порядка: полный обход
  дерева UIA всех окон на этой машине это 116 мс.

`DESK_UI_TIMEOUT_MS`, `DESK_UI_COOLDOWN_MS` и `DESK_UIA_BUDGET_MS` переопределяют
бюджеты. Бюджет воркера меньше серверного, чтобы воркер успел отдать внятный
таймаут раньше, чем сработает breaker снаружи.

Поиск элемента для `computer_invoke` и `computer_set_value` всё ещё идёт с
PowerShell, потому что этим вызовам нужны живые COM-объекты для паттернов.
Нативный слой перебрал только чтение дерева и `computer_element_at`. Ветка OCR
тоже снимает окно через `PrintWindow`, а это синхронный вызов в цель, то есть риск
тот же, что у UIA.

По Mod Organizer 2 на этой машине `computer_invoke` упёрся в бюджет 8 с и вернул
причину вместо зависания:

```
Ошибка: UI Automation зависла на 'invoke|modorganizer': нет ответа 8 с, воркер перезапущен.
Окно не отвечает на UIA — следующие вызовы к нему заблокированы на 90 с.
Дальше: computer_screenshot + computer_ocr или другое окно.
```

Позже `computer_find` по тому же окну занял 8008 мс и был заблокирован так же, а
все остальные окна продолжили работать. Сообщение выше приведено дословно,
вместе с типографским тире, поэтому в этом README оно единственное.

## Игры

Прицеливание в шутере через клик и навести не работает, и количеством кликов это
не лечится. Большинство шутеров читает мышь через raw input: движок берёт только
аппаратные пакеты и полностью игнорирует синтетический ввод, поэтому кнопки
стрельбы работают, а камера не вертится вообще. Обзор делать относительным
движением вместо абсолютного наведения:

```json
{ "tool": "computer_mouse_move", "args": { "dx": 220, "dy": -40, "steps": 20, "stepMs": 8 } }
```

`steps` важен: игры применяют чувствительность к каждому событию мыши, прыжок на
220 пикселей читается как флик, а двадцать мелких шагов читаются как рука. Инструмент
дополнительно замеряет, насколько курсор реально сдвинулся, и добивает остаток:
Windows склеивает синтетическое движение.

| Игра | Переключатель | Проверено |
| --- | --- | --- |
| Counter-Strike: Source (Source 2013) | не нужен, `rawinput` не существует и движок берёт `WM_MOUSEMOVE` | да, вживую |
| CS:GO / CS2 | `cl_rawinput 0` в консоли или `+cl_rawinput 0` в параметрах запуска | не проверено |
| Steam Input («Принудительно Steam Input») | выключить для игры, он подмешивает свой raw input | не проверено |

Графическим редакторам нужен обратный трюк: Paint игнорирует клик, при котором
между нажатием и отпусканием не было движения. Сдвинь на пиксель:

```json
{ "tool": "computer_click", "args": { "x": 800, "y": 400, "nudge": 1 } }
```

А WinForms-кнопке нужно наоборот: курсор должен успеть прийти **раньше** нажатия,
поэтому ей нужен `hoverFirst`, а не `nudge`.

```json
{ "tool": "computer_click", "args": { "x": 590, "y": 189, "hoverFirst": true } }
```

Замерено на одном окне с одними координатами: `nudge: 1` оставлял счётчик на 0,
`hoverFirst: true` двигал его на 1. Оба вызова вернули `ok: true`, потому что на
уровне ввода ничего не сломалось, кнопка просто выбросила клик.

А если координаты пришли с уменьшенного снимка, передай тот же `scale`, вместо
того чтобы считать в уме:

```json
{ "tool": "computer_screenshot", "args": { "region": "0,0,2560,1440", "scale": 0.5 } }
{ "tool": "computer_click", "args": { "x": 640, "y": 360, "scale": 0.5 } }
```

## Безопасность

`computer_close_window` и `computer_launch` разрушительны и требуют явного
`confirm: true`. Текст, прочитанный с экрана, это данные, а не инструкции.

Тесты намеренно только на чтение: снимки, окна, деревья, OCR, буфер, CDP-чтение.
Курсор пользователя не двигается.

## Как пускать агента без присмотра

`confirm: true` у `computer_close_window` и `computer_launch` это заминка против
агента, который выполняет инструкции, а не граница безопасности. Для автономной
работы есть три переключателя, все по умолчанию выключены и включаются
переменными окружения, поэтому обычное поведение не меняется.

```bash
# Показать, что агент собирается сделать, и не дать ему это сделать
DESK_DRY_RUN=1 npx -y desk-mcp

# Писать каждый вызов с параметрами, длительностью и исходом
DESK_AUDIT=1 npx -y desk-mcp
DESK_AUDIT_PATH=C:\logs\desk-mcp.jsonl npx -y desk-mcp   # свой путь

# Отказать любому окну, в заголовке которого нет разрешённой подстроки.
# Проверка идёт до действия, сухой прогон включительно
DESK_ALLOW_TITLES="Блокнот|Notepad" npx -y desk-mcp
```

В сухом прогоне любой изменяющий инструмент возвращает план вместо действия, а
инструменты только на чтение (`computer_read_screen`, `computer_find`,
`computer_screenshot`, `computer_ocr`) продолжают работать: сухой прогон полезен
только если он ещё и читает. Белый список проверяется раньше всего, поэтому план
для запрещённого окна приходит как отказ, а не как зелёный свет.

Строка журнала одна на вызов:

```
2026-10-06 10:07:02 tool=invoke title="Parcel Tracker" ms=33 outcome=ok via= dryRun=True
2026-10-06 10:07:02 tool=invoke title="Roblox" ms=6 outcome=error via= dryRun=True
```

Чего это не даёт: изоляции. Агент в твоей сессии всё равно может перехватить
клавиатуру, пока ты печатаешь. `computer_desktop` уводит окна на другой виртуальный
стол, и это ближайшее к «мешать не буду».

## Ограничения

- **Только Windows.** Это Windows-сервер, и он использует API Windows повсеместно.
- **Эксклюзивный полный экран** (игры, видео): `CopyFromScreen` даёт чёрное. Нужен
  DXGI Desktop Duplication, а это нативная зависимость. Оконные D3D9-заголовки
  через `PrintWindow` проходят, проверено на Counter-Strike: Source.
- **UWP-окна** не отдают ни UIA-, ни MSAA-дерево, чтение уходит в OCR, а значит
  имён элементов не будет.
- **Chromium** требует `--force-renderer-accessibility`, иначе UIA бесполезен и
  нужны CDP-инструменты.
- **Виртуальные рабочие столы** зависят от сборки Windows: на 10 19035
  `VirtualDesktopManager.dll` отсутствует, инструмент вернёт ошибку.
- **Roblox** здесь не проверялся ни разу. Клики, по сообщениям из чужой сессии, не
  срабатывали.
- У поиска элемента для `invoke` и `set_value` пока нет отменяемого таймаута (см.
  выше).

## Проверка

```bash
npm test
```

Ожидаемый хвост: `ИТОГ: 49 ок, 0 провалов, N пропущено`. Пропуск означает, что
какое-то окно на машине не ответило на UI Automation (Steam, 1С или старый WPF
держат COM-вызов открытым), и это поймал circuit breaker. Это свойство чужого
приложения, а не дефект, поэтому прогон от этого не краснеет. Провалов больше нуля
значит настоящую поломку.

Сам breaker проверяется отдельным вторым сервером со смешным бюджетом в 1 мс:
первый вызов должен зависнуть, второй отбиться блокировкой, и оба обязаны
объяснить почему.

## Ловушки Windows

Всё ниже воспроизведено на практике, а не взято из документации.

- Воркер вызывает `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` до любого
  UI-вызова. Без этого UIA и OCR отдают логические единицы, а `SendInput` жмёт в
  физических пикселях, и клик уезжает на десятки пикселей при масштабе 125%.
- `.ps1` обязан быть в UTF-8 **с BOM**, иначе PowerShell 5.1 читает файл как ANSI и
  молча ломает разбор кириллицы.
- В `KEYBDINPUT` поля это `ushort`, а не `uint`. Объявишь `uint`, структура станет
  32 байта вместо 24, `dwFlags` уедет, и `SendInput` не падает, не ругается, не
  возвращает ошибку. Он молча ничего не делает.
- В PowerShell типа `[ushort]` не существует, нужно `[uint16]`.
- Статический C#-метод нельзя назвать `Move` или `Wheel`: вызов падает с
  «does not contain a method named». Обойдено именами `MoveTo`/`ScrollWheel`.
- `SendKeys` не берёт кириллицу вообще. Только `SendInput` с `KEYEVENTF_UNICODE`.
- `ConvertTo-Json -Depth` для дерева UI нужен **больше 12**: узел это примерно два
  уровня вложенности, и при малой глубине вместо объекта молча подставляется строка
  с именем .NET-типа.
- У элементов UIA границы бывают бесконечными, приводить к `Int32` надо с проверкой
  на `IsInfinity` и `NaN`.
- COM-объекты (`AutomationElement`) кэшировать нельзя: протухают при перерисовке
  дерева. Кэшируются только идентификаторы, перед действием делается свежий поиск.
- `Add-Type` компилируется как C# 5: никакой интерполяции `$"..."`, и лямбда не
  может сослаться на локальную переменную, объявленную ниже неё.
- Интерполяция имени перед двоеточием превращает `"$Owner`:$Token"` в `$Owner:`, и
  PowerShell ищет scoped-переменную. Пиши `${Owner}`.
