# Changelog

## 1.4.0 (готовится)

### Исправлено
- **`uia-native.cs` не попадал в npm-пакет.** `worker.ps1:394` грузит его как
  `Join-Path $PSScriptRoot 'uia-native.cs'` и при отсутствии файла молча
  деградирует в `$script:NativeUiaError`. В `package.json` его не было в
  `files`, то есть установка из npm давала сервер **без нативного слоя**: без
  STA-пула, без отменяемого таймаута и в семь раз медленнее на том же дереве.
  Проверено не на глаз: тарбол установлен в отдельный каталог, воркер запущен с
  `DESK_UIA_DIAG=1`, stderr отдаёт
  `UIA-DIAG: RunTree(6000, ...) -> ok=True TID=18 10мс`.
- **Описание пакета было на русском.** `description` в `package.json` показывается
  в поиске npm и в каталогах, поэтому переписан на английский, добавлены
  `repository`, `homepage`, `bugs`, `author`.
- **Английский README показывал русские скриншоты.** Три картинки (`docs/layers`,
  `docs/find`, `docs/ocr`) были нарисованными код-блоками с русским текстом
  («Почта», «ещё два», «таргетинг по смыслу»), и все три стояли в английской
  версии. Заменены на настоящие выводы инструментов с демо-окна и на обычные
  fenced-блоки: код в картинке нечитаем, не переводится и не ищется. Файлы
  удалены.

### Добавлено
- **`examples/demo-app.ps1`**: демонстрационное окно на английском (WinForms,
  `automationId` у всех контролов, лог действий внутри окна). Запускается из
  интерактивной сессии, из агентской не виден: окна, поднятые не из
  пользовательской сессии, на десктоп не попадают.
- **`examples/demo.mjs`**: тот же сценарий как MCP-клиент, find -> set_value ->
  invoke -> verify_state -> clipboard_get. Флаг `--pause` для записи видео,
  `--window` для другого окна. Проверен end to end: `via: ValuePattern`,
  `via: InvokePattern`, `verify_state satisfied`, буфер `"ZX-4471-8820"`.
- **`bench-tokens.mjs`**: замер цены чтения. Считает токены текста (`chars / 4`)
  и токены картинки по двум формулам (Anthropic `w*h/750`, OpenAI high
  `85 + 170*tiles`), плюс задержки. Запуск `npm run bench`.
- **`docs/demo.webm`**: 18 с реального прогона, 940x716, VP9, 196 КБ. Захват
  идёт на живой машине (`ffmpeg -f gdigrab`), курсор в кадре и неподвижен, что и
  есть доказательство: `ValuePattern` и `InvokePattern` двигать его не должны.
- **`mcpb/manifest.json`**: манифест по спецификации MCPB 0.3 для публикации в
  Smithery. У Smithery сейчас нет документированного `server.json` со `schema$`,
  рабочий путь это MCPB-бандл.
- **`docs/PUBLISHING.md`**: что требует аккаунта владельца (npm login, форк и PR,
  `smithery auth login`), готовая строка для `punkpeye/awesome-mcp-servers` с
  бейджем Glama, требования этого списка (CI `check-glama.yml` валит строку без
  бейджа) и раскладка MCPB-бандла.

### Наблюдение
- **Одно плохое приложение тормозит все окна, а не своё.** Вызов, в котором назван
  заголовок окна, сперва платит за UI Automation. На машине с запущенной
  Chromium-игрой (Roblox) **любой** такой вызов ушёл с ~250 мс до 3.0-3.2 с:
  `computer_find` отдавал 3.1 с по Parcel Tracker, 3.0 с по Discord, 3.1 с по
  Edge, 3.1 с по окну консоли и 3.1 с по окну самого репозитория. Вызовы, не
  разрешающие окно, остались быстрыми: `computer_clipboard_get` 1-6 мс, снимок
  области 63 мс, `computer_screenshot` по окну 3.1 с (ему тоже нужен rect).
  **Поокночный breaker это не ловит: виновато не окно, а состояние UIA в системе.**
  Вывод для архитектуры: прямоугольник окна для `screenshot`/`element_at` надо
  брать через `EnumWindows`/`GetWindowRect`, а не через UIA.
- **Открытый пункт подтвердился на живом приложении.** `computer_invoke` по Mod
  Organizer 2 ушёл в бюджет 8 с и вернул честный отказ вместо зависания, позже
  `computer_find` по тому же окну занял 8008 мс и был заблокирован на 90 с. То
  есть поиск элемента без отменяемого таймаута это не теория, а воспроизводимый
  отказ на третьем стороннем приложении.
- **Замеры конкурируют с работой.** Первая запись видео велась одновременно с
  кодированием VP9: CPU забит, UIA-вызовы упирались в бюджет и breaker блокировал
  окно, поэтому в кадр попал пустой лог при «успешном» отчёте скрипта. Рабочая
  схема: снимать дёшево (`libx264 -preset ultrafast`), кодировать и накладывать
  подписи вторым проходом.
- **Демо на 9 шагов это 30 с чистого времени** плюс паузы, а не 18 с, как
  предполагалось. Видео сжато в 1.4 раза (`setpts=0.714*PTS`), подписи расставлены
  по фактическим границам шагов, которые печатает сам скрипт.
- **«Скриншоты тяжёлые, дерево экономит токены» это полуправда, и проверять
  надо замером.** На живой машине поиск одного элемента дешевле картинки того же
  окна в 9.7-147 раз (15-160 токенов против 688-4864), но полное дерево местами
  **дороже** скриншота в 8.5 раза: на Discord лента сообщений это 18765 токенов
  против 2205 у картинки 1793x922. `interactiveOnly` роняет то же дерево до
  1280 токенов. Правильный кадр в README: «look up the element, do not ship the
  window», а не «мы дешевле скриншотов».
- **Локализованная Windows ломает примеры на подписях кнопок.** На русской
  сборке UIA отдаёт `Закрыть`, `Развернуть`, `Свернуть`, `Системное меню`:
  искать элементы надо по `automationId`. Записано в README, потому что это
  ломает агента у пользователя, а не у нас.
- **OCR честно халтурный, и это нормально.** На демо-окне `ZX-4471-8820`
  превращается в `zx-=v-882C`. Пример в README теперь показывает и это.
- Remotion (https://github.com/remotion-dev/remotion) для этой задачи не нужен:
  это рендер видео из React-кода, захвата экрана он не умеет. Захват сделал
  `ffmpeg -f gdigrab` из агентской сессии (проверено кадром, не чёрный), подписи
  наложены `drawtext` с таймингом по шагам сценария.

## После 1.0.0 (1.1.0 - 1.3.0, сведено без разделения по версиям)

### Добавлено
- **Нативный слой обхода UI Automation на C#** (`uia-native.cs`, 916 строк,
  без комментариев). Работа UIA уезжает на выделенный **STA-поток** с
  очередью и жёстким таймаутом: зависший поток помечается, и при следующем
  вызове поднимается новый, старый умирает в фоне. Это наконец даёт
  отменяемость — раньше COM-вызов в зависшее окно был неотменяемым, и
  единственной защитой был watchdog, ронявший весь воркер.
  `Get-UiTree` и `Get-ElementAt` переведены на него; PowerShell-реализация
  осталась запасным путём и включается сама, если файла нет или он не
  скомпилировался. Проверено переименованием файла: результат идентичен,
  `selftest` честно пишет причину.
- `DESK_UIA_BUDGET_MS` — бюджет нативного слоя внутри воркера, по умолчанию
  6 с: он успевает отдать внятный таймаут раньше внешнего circuit breaker'а
  на 8 с.
- `selftest` показывает `nativeUia`, `nativeUiaError` и `uiaBudgetMs`.

### Исправлено
- **Счётчики дерева не видели результат нативного слоя.** `Count-NamedUi` и
  `Count-NamedUiInside` обращались к узлам как `$x['name']` — это работает
  для `ordered`-хэштегов PowerShell, но молча даёт `$null` для
  `PSCustomObject`, который отдаёт `ConvertFrom-Json`. Дерево приходило
  полным, а слой чтения считал его пустым и падал в OCR. Добавлен
  `Get-UiProp`, понимающий оба типа.
- **`textLen` в дереве всегда был 1.** PowerShell отдаёт `.Length` равным 1
  для любого скаляра, а у `TextPatternRange` длины нет — поле было
  константой. Нативный слой отдаёт настоящую длину текста.
- **`computer_browser_tree` возвращал пустое дерево на только что открытой
  странице.** Документ ещё грузился, `querySelectorAll` отдавал пустоту, и это
  выглядело как «на странице нет интерактивных элементов». Наблюдалось на
  свежеподнятом Chrome. Теперь перед разбором DOM ждётся готовности
  документа (`timeoutMs`, по умолчанию 2 с), а в ответе есть поле `ready`.
- **Гонка при подключении к браузеру.** `computer_browser_start` проверял
  `/json/version`, браузер отвечал и тут же умирал, `/json/new` падал — и вместо
  подъёма нового браузера вызывающий получал «fetch failed». Теперь при отказе
  `/json/new` идёт попытка навигации существующей вкладки через
  `Page.navigate`, и только если и она не вышла — поднимается новый браузер.
- **Прогон краснел из-за чужого окна.** Поймано на живом прогоне: окно Steam
  не отвечает на UIA, circuit breaker отрабатывает, а проверка засчитывала
  это как провал инструмента. Теперь такие случаи считаются пропуском с
  пояснением, а сам breaker по-прежнему проверяется отдельным кейсом с 1 мс
  бюджетом. Итог теперь печатается как `ок, провалов, пропущено`.
- **`computer_browser_start` молча терял `url`, если браузер уже запущен с
  debug-портом.** Ответ приходил `ok: true`, а вкладки с адресом не
  появлялось — следующий `computer_browser_tree` честно отвечал «вкладка не
  найдена». Теперь вкладка открывается явно через `/json/new` (именно PUT: на
  GET современные Chrome и Edge отвечают 405), а в ответе видно, что открылось.
- **Поиск вкладки шёл только по URL**, хотя вызывающий почти всегда знает
  заголовок. На подсказку «вкладка не найдена» выводился список заголовков, в
  котором нужная вкладка была, — выглядит как поломка поиска. Теперь ищется и
  по URL, и по заголовку, а в ошибке видно оба.
- **UI Automation больше не глушит сервер на 15 с подряд.** Жёсткий бюджет 8 с и
  главное — circuit breaker по окнам: после зависания ключ `инструмент|окно`
  блокируется на 90 с, и вызовы к этому окну падают мгновенно с объяснением.
  Остальные окна продолжают работать, потому что баг одного приложения не
  должен ронять всё. Через breaker идут `read_screen`, `element_at`, `find`,
  `invoke`, `set_value`, `select_text`, `verify`. Бюджеты переопределяются
  `DESK_UI_TIMEOUT_MS` и `DESK_UI_COOLDOWN_MS`.
- **`computer_batch` обходил circuit breaker целиком.** Пачка исполнялась
  рекурсией внутри воркера, минуя проверки сервера: ни таймаута, ни блокировки,
  а одна зависшая пачка уносила с собой все 50 шагов. Теперь пачка
  разбирается на сервере и выполняется по одному шагу, UIA-шаги — через тот же
  `callUi`. Две реализации больше не разъезжаются: из воркера batch удалён.
- **Объявленный бюджет 8 с не ограничивал реальное ожидание.** Таймер ставился
  после `ensure()`, а `ensure()` при пяти зависаниях подряд спит 30 с. Замер:
  седьмой вызов подряд занимал **30 931 мс**. Теперь весь вызов обёрнут в общий
  дедлайн: тот же шторм даёт максимум **2 012 мс**.
- **Блокировку обходили сменой регистра.** PowerShell `-like` регистронезависим,
  поэтому `ZzzBroken` и `zzzbroken` — одно и то же окно, а ключи получались
  разные. Ключ приведён к нижнему регистру.
- **Утечка временных файлов: по одному 0-байтному `tmpXXXX.tmp` на каждый
  вызов.** `GetTempFileName()` создаёт файл на диске, к нему дописывался
  `.png`, а удалялся только `.png`. Замер: 3 вызова `computer_ocr` давали ровно
  +3 файла. Теперь `+0`. Дефект был и в `computer_ocr`, и в новой ветке
  деградации.
- **`computer_invoke` отчитывался об успехе на неактивном элементе.**
  `InvokePattern.Invoke()` на `enabled=false` в Windows молча ничего не делает
  и не бросает исключение — проверено на Paint: серая кнопка «Копировать»
  вернула `ok: true`, а буфер обмена не изменился. Теперь `invoke`,
  `set_value` и `select_text` отказываются до действия с внятной ошибкой.
  Заодно исключение из `Invoke()` больше не глотается молча: пиксельный
  фоллбэк сообщает, почему он понадобился и что он захватил мышь.
- **Координаты строк OCR локальны относительно области съёмки**, а подсказка
  велела кликать по ним напрямую. Теперь в ответе есть `origin`.
- Фолбэкный регион был жёстко `0,0,2560,1440` — при другом разрешении или
  отрицательном начале виртуального экрана уехал бы. Теперь берётся
  `SystemInformation.VirtualScreen`.
- Просроченные записи circuit breaker чистятся при каждом обращении.
- **Прогон падал из-за гонки в самом автотесте.** Цель для чтения выбиралась
  один раз в начале, а заголовок браузера меняется при каждом открытии и
  закрытии вкладки: между выбором и вызовом окно успевало переименоваться, и
  проверка падала «окно не найдено за 3 с». Теперь цель перевыбирается по
  живому списку, и в счётчик идёт только итоговый результат, а не первый
  неудачный.

### Наблюдение
- **CDP-слой подтверждён на настоящем сайте, не только на `data:`-адресе.**
  `computer_browser_tree` вернул ссылку с готовым селектором
  `body:nth-child(2) > a:nth-child(9)`, `computer_browser_descendants` — DOM с
  границами, `computer_browser_eval` — кириллицу без потерь, а
  `computer_browser_click` по `a[href*='iana']` дал `verified: true` и реальный
  переход с `example.com` на `www.iana.org`. Мышь не двигалась ни разу.
- **`computer_set_value` честно отказывается там, где писать нечем.** Проверено
  на Блокноте: поле редактирования держит `TextPattern`, а не `ValuePattern`
  («неподдерживаемый шаблон»), статус-бар read-only («значение доступно только
  для чтения»). Ложного `ok` нет. Успешную запись проверить не удалось: на этой
  машине не нашлось открытого окна с записываемым `ValuePattern`.
- Живой прогон CDP-слоя на реальной странице подтвердил главное обещание слоя:
  `computer_browser_click` вернул `verified: true` с `trusted: true` и `tag:
  BUTTON`, а страница реально изменилась с «Проба | не нажато» на «НАЖАТО |
  клик прошёл». Мышь при этом не двигается — клик уходит через
  `Input.dispatchMouseEvent`.

Почему не STA-поток с отменой, как это делают в C#: `ScriptBlock` в PowerShell
привязан к своему runspace и на чужом потоке не выполняется. Полная изоляция
требует переноса обхода дерева из PowerShell в C# — это отдельная работа.
Что осталось открытым: сам вызов UIA неотменяемый, первые 8 с против зависшего
окна теряются по-настоящему, а перезапуск воркера роняет параллельный не-UIA
вызов. И ветка OCR-снимка окна использует `PrintWindow`, а он тоже
синхронно ходит в целевое окно — на зависшем окне риск тот же, что у UIA.

### Наблюдение
- Живой прогон в Counter-Strike: Source (de_dust2, локальный сервер):
  `computer_mouse_move` вертит камеру в обе стороны и по вертикали, стрельба
  тратит патроны, клавиатура доходит до игры (меню реагирует на цифры).
  Cvar `rawinput` и `cl_rawinput` в CS:S **не существуют** — «Unknown
  command», движок Source 2013 берёт `WM_MOUSEMOVE`, поэтому синтетический
  ввод мыши работает сразу, без настройки игры. Ранний совет «положи
  `rawinput 0` в autoexec.cfg» был неверен и убран из документации.
  Причина «стреляет, но не вертится» — не rawinput, а абсолютное наведение:
  в шутере курсор залочен в центре окна, `SetCursorPos` там бесполезен.
- Оконные D3D9-заголовки проходят через `PrintWindow` (проверено на CS:S), так
  что «в играх чёрный экран» относится к эксклюзивному полноэкранному
  режиму, а не ко всем играм подряд.
- Paint игнорирует клик без движения: между `WM_LBUTTONDOWN` и `WM_LBUTTONUP`
  нужен `WM_MOUSEMOVE`, иначе не рисуется ничего, а заливка не срабатывает
  вообще. Хватает drag на один пиксель. Описано в ловушках Windows.

### Добавлено
- `computer_click` получил `nudge` — сдвиг курсора между нажатием и
  отпусканием. Это то, что нужно холстам (Paint, Photoshop, Figma) и играм.

  пересчитываются на сервере. Раньше это была постоянная ошибка «промахнулся
  на 20 пикселей».
- `computer_mouse_move` — относительное движение на `dx`/`dy` с дроблением
  на шаги (`steps`, `stepMs`). Для обзора в шутерах: игры применяют
  чувствительность к каждому событию мыши, поэтому один прыжок читается как
  флик, а двадцать мелких шагов — как рука.

### Исправлено
- `computer_batch` не понимал MCP-имена внутри `steps`: `computer_click`
  падал с «Неизвестный инструмент», потому что воркер ждёт короткое `click`.
  Добавлена нормализация (`computer_` отбрасывается) плюс два исключения из
  правила: `computer_window_set_frame` → `set_frame`,
  `computer_verify_state` → `verify`. При промахе ошибка теперь
  перечисляет допустимые имена.
- `stopOnError: false` в `computer_batch` не работал: проверка стояла только в
  ветке успеха, поэтому при ошибке пачка всё равно останавливалась.
  `allOk` больше не выводится как `true` при ошибках, которые проскочили мимо
  остановки.
- Windows склеивает синтетическое движение мыши: запрошенные 5 пикселей давали
  фактические 3. `MoveBy` теперь замеряет реальное смещение и добивает
  остаток, с защитой от зацикливания, если окно вообще не двигает курсор.
- Валидация `steps`, `stepMs` и `scale` пропускала ноль: проверка вида
  `if ($a.scale)` ложна на `0`, и неверное значение молча заменялось
  дефолтом. Заменено на явную проверку `$null -ne`.

## 1.0.0

Первый публичный релиз.

### Наблюдение
- UI Automation → MSAA → Chrome DevTools Protocol: три слоя чтения подряд.
  MSAA включается автоматически, если UIA вернула пустое дерево (Chromium
  без `--force-renderer-accessibility`), с автоматическим наращиванием
  глубины обхода.
- `computer_read_screen`, `computer_find`, `computer_element_at`,
  `computer_browser_tree` — дерево UI и DOM с готовыми дескрипторами.
- `computer_ocr` — текст прямо из пикселей через движок, встроенный в
  Windows (`Windows.Media.Ocr`, ru/en). Ноль моделей.
- `computer_screenshot` — экран, произвольная область или конкретное окно
  через `PrintWindow` (работает на перекрытом и свёрнутом окне).

### Действие
- Ввод текста через `SendInput` + `KEYEVENTF_UNICODE` — кириллица работает,
  `SendKeys` её не берёт.
- `key_down`/`key_up` для удержания, модификаторы в клике, drag,
  `mouse_down`/`mouse_up`, колесо, `wait`.
- `computer_invoke` жмёт через `InvokePattern` **без захвата мыши**;
  `set_value` пишет через `ValuePattern` без фокуса.
- `computer_batch` — до 50 инструментов за один вызов, с остановкой на
  первой ошибке и результатом по каждому шагу.

### Проверка и надёжность
- `computer_verify_state` — предикаты: существует / `value_equals` /
  `enabled` / `selected`; `unknown` честно отличается от успеха.
- CDP-клик с двойным доказательством: проба в странице **или** смена URL.
- Таймаут вызова убивает зависший воркер и поднимает новый; после пяти
  зависаний подряд — пауза 30 с вместо отказа.
- `computer_close_window` и `computer_launch` требуют `confirm: true`.

### Ограничения (осознанные)
- Эксклюзивный полный экран: нужен DXGI Desktop Duplication, не делаем.
- Виртуальные рабочие столы: зависят от сборки Windows.
- UWP-окна не отдают ни UIA, ни MSAA-дерево.
